File Server Architecture

공용 이미지 서버의 현재 구조를 기능 경계 기준으로 설명합니다. ImageAsset/ImageVariant 권위 메타데이터, staged upload, 비동기 variant job, filesystem reconciliation, Kafka outbox, 복제 cache invalidation과 Nginx 기반 실제 Docker 통합 경로까지 포함합니다.

1. 이번 구조 변경의 핵심

이미지 파일 자체만 저장하고 telemetry에서 현재 이미지를 추론하던 구조를, PostgreSQL metadata와 filesystem object를 함께 관리하는 명시적 수명주기로 변경했습니다. 작업 단계 번호는 계획 문서의 이력에만 남기고 운영 코드·명령·환경변수·metric은 기능명으로 통일합니다.

영역 이전 현재
이미지 원장 telemetry/lifecycle event에서 활성 이미지를 추론 ImageAsset이 원본의 권위 source, ImageVariant가 파생 파일 상태를 관리
업로드 파일 저장 후 후속 작업을 직접 수행 Pending metadata → stage write → 검증 → atomic rename → Ready/outbox transaction
PRE_GENERATE 업로드 요청 안에서 동기 Sharp 처리 Ready 이후 durable variant job을 Kafka로 전달하고 worker가 비동기 생성
삭제 filesystem/cache 인스턴스에 즉시 삭제 요청 Deleting → Deleted 상태 전이, 모든 variant와 Kafka cache invalidation을 하나의 eventId로 추적
복구 운영자가 파일과 DB를 수동 비교 lease 기반 reconciliation이 stale Pending, orphan, missing file, Deleting, checksum 불일치를 반복 복구
운영 명칭 구현 단계 번호가 파일·환경변수·metric에 노출 image-lifecycle, image-asset, imageLifecycle처럼 기능 중심 이름 사용
현재 추적 파일과 런타임 식별자에는 단계 번호 기반 이름이 없습니다. 계획 문서의 “단계 5” 표현은 구현 순서를 설명하는 이력일 뿐 런타임 계약이 아닙니다.

2. 전체 런타임 구조

실제 통합 환경의 외부 HTTP 진입점은 Nginx 하나입니다. Nginx가 조회를 cache로, 업로드·삭제를 storage로 보냅니다. resize와 storage 내부 GET은 내부 API key와 서명된 tenant context로만 호출됩니다. variant worker와 reconciliation scheduler는 현재 storage 프로세스에 함께 배치되지만, DB lease/CAS와 Kafka consumer group으로 중복 실행을 제어합니다.

3. 실제 Docker · Nginx 통합 구조

Travel Cloud 통합 하네스는 PostgreSQL, ACL Kafka, migration/topic bootstrap, storage/resize/cache/telemetry-api와 Nginx를 하나의 Docker Compose project로 실행합니다. HTTP mock이나 Kafka mock을 사용하지 않으며 Nginx가 유일한 외부 이미지 HTTP 진입점입니다.

4. 계속 보존되는 공통 계약

Tenant namespace 모든 image path는 clientServiceId 정책과 namespace 검증을 통과해야 합니다. 다른 tenant의 path/imageKey 접근은 403입니다.
Signed internal context cache → resize → storage 내부 호출은 internal API key와 서명된 tenant context를 함께 전달합니다.
Multipart path-before-file 업로드 parser는 path field가 file part보다 먼저 도착해야만 파일을 수락합니다.
Event delivery 공용 event contract, eventId 멱등성, manual offset commit, retry/DLQ/terminal failure 의미를 유지합니다.
Query contract PostgreSQL filtering/aggregation, opaque keyset cursor, bounded take와 legacy numeric cursor adapter를 유지합니다.
HTTP resilience 기본 2초 timeout, AbortSignal, GET-only bounded retry와 401/403/404/502/503/504 status 보존을 유지합니다.

5. 앱과 모듈의 책임

storage staged upload/delete, authoritative metadata transaction, filesystem adapter, lifecycle outbox, variant job publish/consume, reconciliation과 내부 Ready object 조회를 담당합니다.
resize cache miss에서만 내부 호출되며 Ready source/variant를 읽어 pass-through 또는 on-demand Sharp 처리를 수행합니다.
cache 외부 GET 진입점입니다. tenant/image/variant singleflight, 총 byte budget eviction과 Kafka invalidation consumer를 가집니다.
telemetry-api telemetry/lifecycle Kafka consumer, PostgreSQL query/aggregation, authoritative admin image 목록, retention과 운영 health를 제공합니다.
admin-web 서비스/API key/subscription/resize policy 관리와 dashboard, event, active image, lifecycle 상태를 표시합니다.
공유 library @file/database가 metadata repository를, @file/telemetry-contracts가 lifecycle/variant/invalidation payload를, @file/image-contracts가 path와 storage key 규칙을 제공합니다.

6. Staged upload와 성공 시점

같은 (clientServiceId, logicalPath, name)은 하나의 asset으로 수렴합니다. HTTP 201은 source가 Ready가 되고 lifecycle outbox·variant job ledger가 같은 DB transaction에서 commit된 뒤에만 반환됩니다. variant 생성과 Kafka/cache 전파 완료까지 의미하지는 않습니다.

  • cache → resize → storage 기본 deadline은 2초이며 모두 AbortSignal을 전달합니다.
  • 자동 retry는 멱등 GET에만 1~2회 bounded backoff로 적용합니다. upload/delete에는 적용하지 않습니다.

  • response bytes, image pixel 수와 Sharp concurrency에 상한이 있습니다.

12. Health, metric과 DB 조회

/health/live 프로세스 event loop와 HTTP server가 살아 있는지만 나타냅니다. 외부 의존성 장애로 false가 되지 않습니다.
/health/ready PostgreSQL, Kafka, 필수 upstream, filesystem/storage probe와 image lifecycle backlog 기준을 반영합니다.
Kafka broker end offset과 consumer group committed offset으로 실제 lag를 계산합니다. reconnect 중에는 ready=false입니다.
operationalMetrics.imageLifecycle asset/variant/job 상태 count, oldest active age, reconciliation과 runtime job/invalidation/delete metric을 제공합니다.

telemetry/lifecycle 목록은 (occurredAt, eventId) opaque keyset cursor와 bounded take를 사용합니다. filter, sort, pagination과 dashboard aggregation은 Node memory가 아니라 PostgreSQL에서 수행합니다. Retention은 telemetry 90일, published outbox 30일 기본값으로 batch/sleep/lock timeout을 적용하며 unpublished outbox는 삭제하지 않습니다.

readiness 실패는 이미지 404가 아닙니다. 호출자는 503/timeout을 재시도 가능한 가용성 장애로 처리하고, 권한 오류와 실제 404를 구분해야 합니다.

  1. 두 expand migration을 적용하고 backfill index의 indisvalid/indisready=true를 확인합니다.
  2. IMAGE_ASSET_METADATA_WRITES_ENABLED=true, dual-read enabled 상태로 storage를 배포합니다.
  3. dry-run 후 batch backfill을 반복 실행하고 snapshot이 완료됐는지 확인합니다.
  4. variant worker와 reconciliation을 활성화하고 health/lag/DLQ를 관찰합니다.
  5. writer와 inflight 요청을 drain하고 outbox backlog 0, Kafka high watermark 도달과 consumer lag 0을 확인합니다.
  6. ingestion drain confirmation을 설정한 final cutover audit에서 gap 0을 확인합니다.
  7. storage와 telemetry-api의 dual-read를 함께 끄고 authoritative read로 전환합니다.
  8. 전환 기간이 끝난 뒤에만 legacy adapter/flag 제거를 별도 contract 작업으로 수행합니다.
Rollback은 schema나 backfilled row를 삭제하지 않습니다. dual-read를 다시 켜고 필요한 경우 metadata write를 잠시 끈 뒤, variant worker/reconciliation을 중지해 기존 HTTP path로 복귀합니다.

15. Production filesystem 위치

현재 production storage 컨테이너는 Docker named volume file_dump_volume을 assets 경로에 mount합니다. 컨테이너를 재생성해도 volume은 유지되지만 DB metadata와 filesystem backup/restore 시점을 함께 맞춰야 합니다. 

docker run -d \
  --env-file ${{ secrets.STORAGE_ENV_PATH }} \
  -v file_dump_volume:/usr/index/apps/storage/dist/apps/storage/assets \
  -p ${{ secrets.STORAGE_PORT }}:${{ secrets.STORAGE_PORT }} \
  --name file_server_storage \
  --restart always ghcr.io/.../storage:latest

docker volume inspect file_dump_volume
다중 호스트 shared-filesystem failover와 운영 규모 장시간 soak/restart 검증은 아직 남아 있습니다. Object storage 전환 전까지 DB backup만으로는 이미지 복구가 완결되지 않습니다.
