File Server 구조 정리

여러 Client Service가 공용으로 사용하는 이미지 서버의 현재 구조입니다. DB 기반 서비스 레지스트리, API key guard, Kafka telemetry/lifecycle, outbox, pre-generate 리사이징 정책과 admin-web 운영 흐름까지 포함합니다.

Storage / Resize / Cache Telemetry API Admin Web PostgreSQL + Prisma Kafka

1. 전체 런타임 구조

storage, resize, cache의 이미지 라우트는 모두 x-client-api-key를 DB에서 검증합니다. 표준 telemetry는 file.image.events.v1로, Client Service 후속 업무용 lifecycle은 file.image.lifecycle.v1로 나뉘며, 기존 image-topic은 호환용으로 유지됩니다.

2. 앱별 책임

storage 원본 업로드/삭제/조회, legacy event 발행, telemetry 발행, lifecycle outbox 저장/재시도, pre-generate variant 생성을 담당합니다.
resize storage에서 원본을 가져와 on-demand 리사이징을 수행하고 결과를 바로 응답합니다.
cache on-demand resize 결과를 NodeCache 메모리에 저장합니다. 서버 재시작 시 캐시는 사라집니다.
telemetry-api Client Service/API key/subscription/resize policy 관리, Kafka consumer, event 저장, dashboard와 추천 API를 제공합니다.
admin-web 서비스 레지스트리, API key, lifecycle subscription, 리사이징 정책, 추천 반영, dashboard/events/images/lifecycle 조회 화면을 제공합니다.
libs PrismaService, API key hash/verify, Client Service guard, request context, telemetry/lifecycle event contract를 공유합니다.

3. 신규 Client Service 추가와 재시작 기준

새 서비스는 admin API 또는 admin-web에서 DB에 등록하고 API key를 발급하면 됩니다. storage, resize, cache는 요청마다 key prefix와 hash를 DB에서 조회하므로 서비스 추가만으로는 재시작이 필요 없습니다.

대상 신규 서비스 후 재시작 재시작이 필요한 경우
storage / resize / cache 불필요 DATABASE_URL, CLIENT_API_KEY_PEPPER, 서버 URL, Kafka broker, 코드 변경
telemetry-api 불필요 DB/Admin token/Kafka 설정, Prisma migration, 코드 변경
admin-web 불필요 TELEMETRY_API_BASE_URL, TELEMETRY_ADMIN_TOKEN, 코드 변경
Kafka 불필요 topic 최초 생성, broker/보안/ACL 정책 변경

4. 업로드와 lifecycle outbox 플로우

업로드 성공/실패 lifecycle event는 먼저 image_lifecycle_outbox에 저장된 뒤 Kafka로 발행됩니다. 발행 실패 시 scheduled publisher가 재시도하고, 전달 보장은 at-least-once입니다. Client Service는 eventId를 idempotency key로 처리해야 합니다. 

sequenceDiagram
	autonumber
	participant C as ClientService
	participant S as Storage
	participant DB as PostgreSQL
	participant K as Kafka
	participant T as TelemetryAPI
	participant CS as ClientConsumer

	C->>S: POST /image with x-client-api-key
	S->>DB: API key and service status lookup
	S->>S: temp file write and sharp normalize
	S->>S: save original to assets volume
	S->>DB: insert image_lifecycle_outbox
	S->>K: publish file.image.events.v1
	S->>K: publish legacy image-topic
	S-->>C: 201 Created
	S->>DB: read pre-generate policy
	alt mode is PRE_GENERATE
		S->>S: create active resize variants
		S->>K: publish image.resize.completed or failed telemetry
	else mode is ON_DEMAND
		S->>S: keep upload-only flow
	end
	S->>K: outbox publisher sends file.image.lifecycle.v1
	T->>K: consume telemetry and lifecycle topics
	T->>DB: save telemetry_events and image_lifecycle_events
	CS->>K: consume lifecycle with own consumer group
현재 pre-generate 파일명은 원본과 같은 directory에 <원본>__w<width|auto>_h<height|auto>.<format> 형태로 저장됩니다.

7. 리사이징 정책과 추천

Client Service별 정책은 ON_DEMAND 또는 PRE_GENERATE입니다. PRE_GENERATE에서는 업로드 직후 활성 variant(width/height/format)를 미리 생성하고, 결과는 telemetry event로 남깁니다. 추천 API는 과거 on-demand resize 성공 이벤트 중 cacheKey가 없는 요청만 집계하여 pre-generate 후보를 보여줍니다.

8. admin-web 운영 화면

  • /dashboard: 서비스별 KPI, cache hit/miss, resize/upload 추이
  • /events: 표준 telemetry event 조회와 필터
  • /lifecycle-events: upload completed/failed 업무 이벤트 조회
  • /images: imageKey별 요청/resize/cache/failure 집계
  • /services: 서비스, API key, lifecycle subscription, 리사이징 정책 관리
  • /resize-recommendations: pre-generate 후보 조회와 정책 반영

9. 실서버 저장 위치

.github/workflows/storage.yml 기준 production storage 컨테이너는 Docker named volume file_dump_volume을 assets 경로에 mount합니다. 

docker run -d \
  --env-file ${{ secrets.STORAGE_ENV_PATH }} \
  -v file_dump_volume:/usr/index/apps/storage/dist/apps/storage/assets \
  -p ${{ secrets.STORAGE_PORT }}:${{ secrets.STORAGE_PORT }} \
  --name file_server_storage \
  --restart always ghcr.io/.../storage:latest
컨테이너를 삭제/재생성해도 file_dump_volume은 유지됩니다. 호스트 실제 경로는 docker volume inspect file_dump_volume으로 확인합니다.

10. end-to-end 점검 순서

  1. PostgreSQL/Kafka topic을 준비하고 Prisma migration을 적용합니다.
  2. telemetry-api를 켜고 Client Service를 등록한 뒤 API key를 발급합니다.
  3. storage/resize/cache를 켜고 같은 CLIENT_API_KEY_PEPPER와 DB를 보게 합니다.
  4. API key로 업로드, 원본 조회, resize, cache hit/miss를 수행합니다.
  5. Client Service consumer group으로 file.image.lifecycle.v1 이벤트를 소비합니다.
  6. admin-web에서 dashboard/events/lifecycle/images/services/recommendations를 확인합니다.
  7. PRE_GENERATE 정책을 켠 서비스 업로드에서 variant 생성과 resize telemetry를 확인합니다.
명령어 기반 상세 절차는 repository 루트의 INSPECT.md를 기준으로 점검합니다.
